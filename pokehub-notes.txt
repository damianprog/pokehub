---
Krok 1: co się dzieje, gdy przeglądarka wchodzi na jakiś adres

Kiedy przeglądarka odpytuje adres, np. https://twojaapka.pl/api/auth/session, wysyła do twojego serwera żądanie HTTP (request). Serwer musi na nie odpowiedzieć (response). To jest cała istota backendu: przychodzi żądanie → serwer coś robi → odsyła odpowiedź.

Żądanie ma dwie ważne części:
- adres (ścieżka), np. /api/auth/session
- metodę — czasownik mówiący „co chcę zrobić":
  - GET = „daj mi coś, tylko czytam" (np. „daj mi dane sesji")
  - POST = „przyjmij coś, wykonaj akcję" (np. „zaloguj mnie", „wyloguj mnie")

Ten sam adres może obsługiwać oba czasowniki inaczej. /api/auth/signout na GET może pokazać stronę „czy na pewno wylogować?", a na POST faktycznie wylogować.

---
Krok 2: jak Next.js wie, który kod obsługuje który adres

W Next.js struktura folderów = struktura adresów. To się nazywa file-based routing. Nie ma osobnego pliku, gdzie ręcznie wpisujesz „adres X → funkcja Y". Zamiast tego:                              
- Folder src/app/api/auth/[...nextauth]/ odpowiada adresowi /api/auth/...
- Plik route.ts w tym folderze to kod, który odpowiada na żądania HTTP pod tym adresem.                                                                                                              
I teraz najważniejsza konwencja Next.js:

▎ Plik route.ts musi wyeksportować funkcje o nazwach metod HTTP. Jeśli wyeksportujesz funkcję GET, Next.js wywoła ją przy żądaniach GET. Jeśli POST — przy żądaniach POST.
                                                                                                                                                                                                     Czyli gdybyś pisał to ręcznie, wyglądałoby tak:
                                                                                                                                                                                                     export function GET(request) {
  // co zrobić, gdy ktoś zrobi GET na ten adres
  return new Response("...");                                                                                                                                                                        }

export function POST(request) {
  // co zrobić, gdy ktoś zrobi POST na ten adres                                                                                                                                                       return new Response("...");
}                                                                                                                                                                                                    
Next.js szuka w route.ts eksportów o nazwach GET, POST, PUT, DELETE itd. i podpina je automatycznie. To jest cały „kontrakt": eksportuj funkcję nazwaną jak metoda HTTP, a Next.js ją wywoła przy tejmetodzie.

                                                                                                                                                                                                     Zwykły folder login/ łapie dokładnie jeden adres: /login.

Folder w nawiasach [...nextauth] to catch-all — łapie wszystko, co jest głębiej pod tą ścieżką:
                                                                                                                                                                                                     - /api/auth/signin

Teraz wróćmy do auth.ts. Pamiętasz, że NextAuth({...}) to fabryka, która zwraca zestaw narzędzi:

  POST: function(request) { /* cała logika NextAuth dla POST */ },
}

Metafora, która to spina

Wyobraź sobie budynek z wieloma drzwiami (adresami):

- Next.js = recepcja, która patrzy na adres i metodę żądania i mówi „to zadanie dla route.ts spod /api/auth, metoda GET → wołam eksport GET z tego pliku".
- route.ts = tabliczka na drzwiach mówiąca „na pukanie GET odpowiada ta osoba, na POST ta". Sama nic nie robi — tylko wskazuje, kto obsługuje.
- handlers (z NextAuth) = faktyczny pracownik, który wykonuje robotę (logowanie, call

route.ts jest celowo pusty z logiki, bo jego jedyne zadanie to połączyć adres URL z gotowym pracownikiem NextAuth. Cała mądrość siedzi w handlers, a handlers powstało z konfiguracji w auth.ts (adapter

- handlers = obiekt { GET, POST } z gotową logiką autoryzacji, wyprodukowany przez Nets tylko go re-eksportuje, żeby spełnić konwencję Next.js.

What Zustand is

Zustand is a tiny state-management library for React. A "store" is just a container for some state plus the functions that update it, created once with create(). Any component that calls the store's hook (e.g. useWishlistStore()) automatically re-renders when the piece of state it reads changes — no <Context.Provider> wrapping needed, no prop drilling, no reducers/actions boilerplate like Redux.

Compare it to useState: useState lives inside one component and dies when that component unmounts. A Zustand store lives outside the component tree, in module scope, so multiple unrelated components can read and write the same state, and it survives across renders/remounts of whatever components use it.

Why the codebase already uses this pattern

PokeHub already had two stores before wishlist:
- src/store/auth-modal.ts — mode: "login" | "signup" | null. The Nav button, the landing page CTA, and the FavoriteButton/WishlistButton (when an anonymous user clicks) all need to open the same modal instance mounted once in the root layout. There's no parent-child relationship between "the button that triggers it" and "the modal that renders it" — a store is the natural bridge.
- src/store/review-composer.ts — similar idea for the review composer modal.

How it's used in the wishlist feature specifically

Look at src/store/wishlist.ts. The reason it exists comes down to one thing: the wishlist state needs to be visible to several sibling components that aren't parent/child of each other.

On /p/[slug], wishlist-related UI is spread across up to 7 different components: WishlistButton (desktop, in PokemonActions), WishlistButton (mobile, in PokemonMobileHero), WishlistBadge (desktop corner pill), WishlistMobileBadge (mobile pill), WishlistCountFooter (desktop "N of 3" line), WishlistCapacityNotice (desktop panel), WishlistCapacitySheet (mobile sheet). All of them need to agree on the same live isWishlist/count value at the same time. If you click "wishlist" on desktop, the mobile badge (which is also mounted — both surfaces render simultaneously, just CSS-hidden by breakpoint per the md: pattern this codebase uses) needs to reflect that instantly too, without a page reload.

Concretely:

export const useWishlistStore = create<WishlistStore>((set, get) => ({
  pokemonId: null,
  isWishlist: false,
  count: 0,
  capacityNoticeOpen: false,
  hydrate: (pokemonId, isWishlist, count) => { ... },
  setWishlist: (isWishlist, count) => set({ isWishlist, count }),
  openCapacityNotice: () => set({ capacityNoticeOpen: true }),
  closeCapacityNotice: () => set({ capacityNoticeOpen: false }),
}));

The flow:
1. Server renders first. page.tsx fetches the real isWishlist/count from the DB and passes them as initialIsWishlist/initialWishlistCount props to every component that needs them.
2. WishlistButton hydrates the store on mount with those server values via hydrate().
3. Every other component reads through useWishlistState(pokemonId, initialProps) — a small hook that returns the store's live value once hydrated, or falls back to the server-rendered prop before that. This means components never show a flash of wrong state, and they don't each need their own hydration logic.
4. Clicking the button does an optimistic update — setStoreWishlist(nextIsWishlist, nextCount) flips the store immediately (instant UI feedback), then calls the setWishlist server action. If the action fails, it calls setStoreWishlist again with the old values to revert.
5. Because all the badge/footer/notice components are reading the same store, that one optimistic update is what makes the desktop badge, the mobile badge, and the "N of 3" footer all update together without any of them talking to each other directly.

The pokemonId guard on hydrate exists because both WishlistButton instances (desktop and mobile) mount at the same time and each runs its own hydrate effect — without the guard, whichever one's effect ran second would silently overwrite an already-in-flight optimistic update with the stale server prop.

In short: Zustand's role here isn't complex global app state — it's a lightweight way to let a cluster of sibling components on one page share one piece of live, optimistically-updated state, following the exact same pattern (create(), a typed interface, plain setter functions) already established by auth-modal.ts and review-composer.ts.
